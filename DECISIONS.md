# Decisions

Append-only. Every choice between alternatives, with the reasoning.

## Decisions

### Migration created with `migrate diff`, then hand-edited, and checked in a rolled-back transaction
- Decision: how to produce the init migration before the database is in use.
- Chosen: `prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script` for the table/index/FK SQL, then the four CHECK constraints appended by hand (AGENTS.md rule 6), and the whole file run inside BEGIN ... ROLLBACK against the local records-slice container to prove it executes. Prisma has not applied it yet, so `prisma migrate dev` will still record it as pending.
- Rejected and why: `prisma migrate dev --create-only` first — equivalent output, but it needs a running database just to write a file, and this was done before the owner had approved the schema.
- Files: prisma/migrations/20260930120000_init_records/migration.sql

### users and sessions: what came over from auth-slice's schema
- Decision: which of auth-slice's `users`/`sessions` columns and constraints to keep.
- Chosen: everything is kept exactly (types, defaults, `users_email_key`, `users_email_lowercase_trimmed`, `users_name_length`, session id = SHA-256 hash of the token, `sessions_user_id_fkey` ON DELETE CASCADE, `sessions_user_id_idx`) EXCEPT `users.email_verified_at`, which is dropped.
- Rejected and why: keeping `email_verified_at` — its only readers are email verification, which this slice does not have. A nullable column nothing ever sets would leave seeded users permanently "unverified" and invite a dead check in sign-in and the dashboard.
- Files: prisma/schema.prisma, prisma/migrations/20260930120000_init_records/migration.sql

### projects: public_id is generated by the database
- Decision: where a project's public_id comes from.
- Chosen: a database default, `replace(gen_random_uuid()::text, '-', '')` (32 hex characters, 122 random bits, independent of the primary key's own gen_random_uuid()), plus a CHECK that it is 16-64 characters of `[A-Za-z0-9_-]`.
- Rejected and why: generating it in application code (a nanoid-style helper) — a second place a row can get a bad or missing value, and a raw-SQL insert or seed script would have to remember it. Also rejected: reusing the primary key as the URL id, which is exactly what the brief rules out.
- Files: prisma/schema.prisma, prisma/migrations/20260930120000_init_records/migration.sql

### projects: both requested indexes, although one is a prefix of the other
- Decision: whether to create `projects(user_id)` as well as `projects(user_id, created_at)`.
- Chosen: both, as the brief specifies. Postgres can serve a `user_id`-only lookup from the composite index, so `projects_user_id_idx` is likely redundant; it costs a little write time and disk. Revisit after the CRUD queries exist and `EXPLAIN` shows which index they use.
- Rejected and why: dropping the single-column index unasked — the brief named it explicitly.
- Files: prisma/schema.prisma

### audit_log: no foreign keys, no indexes
- Decision: how audit_log relates to users and projects.
- Chosen: `user_id` and `record_public_id` are plain columns with no foreign key. A key to projects is impossible by design (the row is gone). A key to users with CASCADE would delete the trail when an account is deleted, and one without CASCADE would block deleting users. No index yet: nothing reads this table until a later task needs it.
- Rejected and why: `user_id` FK to users — see above. An index on (user_id, created_at) — nothing queries it yet; add it when a reader exists.
- Files: prisma/schema.prisma

### projects.description has no database length limit
- Decision: whether to cap `description` with a CHECK, as `title` is.
- Chosen: no cap for now; the brief asked for a length check only on `title`. The cap belongs in the shared Zod schema when the create/update routes are built, and the same task should decide whether to mirror it as a CHECK.
- Rejected and why: inventing a limit the brief did not give.
- Files: prisma/schema.prisma

### Drop projects_user_id_idx (supersedes "both requested indexes")
- Decision: whether to keep the single-column index on projects(user_id).
- Chosen: dropped, on the owner's instruction. Only `projects_user_id_created_at_idx` (user_id, created_at) remains; a user_id-only lookup uses its leftmost column. The migration was edited before it was ever applied, so there is no separate "drop index" migration.
- Rejected and why: keeping it — redundant write overhead. The earlier entry recording both indexes is left as written (append-only) and is superseded by this one.
- Files: prisma/schema.prisma, prisma/migrations/20260930120000_init_records/migration.sql

### Deliberately excluded from the auth port
- Rate limiting on sign-in: auth-slice's version stores counters in a `rate_limit_buckets` table, and the brief scoped this slice to `users` and `sessions`. Sign-in here has no brute-force throttle; add one (with its table) if the brief needs it.
- /api/auth/me: it would return `SafeUser`, which contains the internal user id.
- error.tsx, global-error.tsx, not-found.tsx: not needed for the slice.

- Chosen: kept both (approved). The dashboard is where sign-in lands and what proxy.ts protects; sign-out is how one browser switches between alice and bob when testing ownership.
- Rejected and why: sign-in only — leaves nowhere to land and no way to change user without clearing cookies by hand.

- Chosen: alice@example.com and bob@example.com, password `records-slice-test-1`, from payment-slice's scripts/seed.ts with carol removed and the password renamed. Upserts by email, refuses non-local databases, and can be re-run. Two users are enough to test ownership and cross-user access.

### projects.description length limit, mirrored in the database
- Decision: whether to cap description in the database as well as in Zod (open question from the schema entry).
- Chosen: 2000 characters, in `authConfig.projects.descriptionMaxLength`, enforced by the Zod schema AND a new CHECK `projects_description_length` (NULL allowed), added as its own migration, `20260930140000_projects_description_length`. The first migration is untouched.
- Rejected and why: Zod only: a raw SQL insert or a future bug could still store an unbounded string, and the title already has a database guarantee.
- Files: prisma/migrations/20260930140000_projects_description_length/migration.sql, src/config/auth.ts, src/lib/validation/projects.ts

### Where project queries live, and how every one is scoped
- Decision: how to make "owner inside the query" hard to get wrong.
- Chosen: every read and write of projects goes through src/lib/projects/queries.ts, whose functions all take the user id from the session and put it in the query's own filter. List: `WHERE user_id = $1`. Detail: `WHERE public_id = $1 AND user_id = $2`. Create: `user_id` comes from the session, and the Zod schema drops any `user_id` in the body. Delete: see the next entry. Every select names its fields, so the internal `id` is never returned; API JSON uses camelCase `publicId`, matching `createdAt`.
- Rejected and why: queries written inline in each page or route: easy to forget the owner condition in one of them.
- Files: src/lib/projects/queries.ts, src/app/projects/page.tsx, src/app/projects/[publicId]/page.tsx, src/app/api/projects/route.ts, src/app/api/projects/[publicId]/route.ts

### Delete: one CTE statement instead of a transaction
- Decision: how to delete a project and write its audit row together.
- Chosen: one parameterised statement: `WITH deleted AS (DELETE FROM projects WHERE public_id = $1 AND user_id = $2 RETURNING public_id, title) INSERT INTO audit_log (...) SELECT ..., 'project.deleted', public_id, jsonb_build_object('title', title) FROM deleted RETURNING record_public_id`. One statement is atomic, so the audit row cannot exist without the delete or the reverse; a wrong owner or missing id deletes nothing and inserts nothing, and the route answers 403. The audit title comes from the deleted row itself.
- Note on wording: AGENTS.md says the audit row is written "before the row disappears". Inside one statement there is no before and after; the guarantee is atomicity (both or neither), and the audit data is read from the row being deleted. If a reviewer wants the literal order, the first version below does it.
- Rejected and why: the first version, an interactive transaction (scoped `findFirst`, `auditLog.create`, scoped `deleteMany`). It works and audits first, but costs 4 logged statements plus BEGIN, and the find-then-delete gap is the shape the ownership rule tries to avoid, even though the delete is still scoped.
- Files: src/lib/projects/queries.ts

### A project that is not yours: 403 for pages and API alike, same page for "someone else's" and "does not exist"
- Decision: what a signed-in user sees for a project they don't own.
- Chosen: pages call `forbidden()` and render src/app/projects/[publicId]/forbidden.tsx with a real HTTP 403 and identical wording whether the id belongs to another user or to nobody. The API returns `403 FORBIDDEN` from the same zero-rows result. A malformed id (fails the public-id format) skips the query and gets the same 403. No session gives a redirect to /sign-in on pages and 401 on the API.
- Rejected and why: 404 (the brief asked for 403-equivalent); a page that says "this belongs to someone else" (reveals the id exists); 400 for a malformed id (a second, distinguishable response).
- Cost: `forbidden()` needs `experimental.authInterrupts: true` in next.config.ts in Next 16.3.5. Anything experimental can change between releases.
- Files: next.config.ts, src/app/projects/[publicId]/page.tsx, src/app/projects/[publicId]/forbidden.tsx, src/app/api/projects/[publicId]/route.ts

### session.ts changed: relationJoins preview feature
- Decision: how to get the session and its user in one query.
- Chosen: `previewFeatures = ["relationJoins"]` in the Prisma generator and `relationLoadStrategy: "join"` in `validateSession`. This edits a file the brief said to bring over as-is; the change is one option and a corrected comment, and it removes one query from every authenticated request. See BUILD_LOG.md.
- Rejected and why: leaving it: the two-query lookup doubled the cost of the simplest actions. A raw SQL join: loses Prisma's typing for no gain over the join option.
- Files: prisma/schema.prisma, src/lib/auth/session.ts

### Query-count helper (dev only)
- Decision: how to measure queries per action.
- Chosen: with `NODE_ENV=development`, db.ts asks Prisma for query events and src/lib/dev/query-count.ts records each SQL statement; `countQueries(label, fn)` logs "[query-count] label: N" plus the SQL. It wraps the list, detail, create and delete handlers, including the session lookup. It compares statements recorded before and after, so it is exact only when one request runs at a time (as when measuring by hand). Prisma's log does not report BEGIN, so a transaction's count is one lower than what reached Postgres (not verified on the Postgres side).
- Rejected and why: `$extends` counting operations: it counts Prisma calls, not SQL statements. Counting on the Postgres side: needs server config changes.
- Files: src/lib/dev/query-count.ts, src/lib/db.ts

### Query counts, measured (statements Prisma logged per request, session lookup included)
| Action | First version | Final | Session lookup | The action's own queries, first to final |
|---|---|---|---|---|
| List (GET /projects) | 3 | 2 | 2 to 1 | 1 to 1 (always one) |
| Detail (GET /projects/[publicId]) | 3 | 2 | 2 to 1 | 1 to 1 (always one) |
| Create (POST /api/projects) | 3 | 2 | 2 to 1 | 1 to 1 (always one INSERT ... RETURNING) |
| Delete (DELETE /api/projects/[publicId]) | 6 | 2 | 2 to 1 | 4 to 1 (find, audit insert, delete, COMMIT; BEGIN not logged) |

- The first versions were written the natural way (scoped `findMany`/`findFirst`/`create`, and the interactive-transaction delete) and measured before any optimisation. List, detail and create were already one query each; the only improvement there is the session lookup. The real change is delete: 4 statements plus BEGIN became 1. A repeat delete of an already-deleted id costs the same 2 and returns 403 with no audit row.
- Numbers come from the `[query-count]` lines in the dev server log during a curl run, then again over a full browser run (list 2, detail 2, create 2, delete 2 on every occurrence).

### Resetting the local database
- Decision: how to reach a clean state before generating evidence.
- Chosen: `TRUNCATE audit_log, projects, sessions, users` through psql in this repo's own container, then re-run the seed script (alice and bob get fresh rows and the test password). Done before the audit and again before the screenshots, so the audit_log screenshot shows exactly one row: the deletion made through the UI.
- Rejected and why: `docker compose down -v` (AGENTS.md forbids volume removal commands); adding a reset mode to the seed script (more surface than a one-line truncate needs).
- Files: none

### Access-control audit: a script in the repo, run against a production build
- Decision: how the audit table is produced and what it runs against.
- Chosen: scripts/check-access-control.ts (`npm run check:access`) makes every attempt over real HTTP as alice and bob and writes docs/evidence/access-control-audit.md, so the table can be regenerated instead of hand-typed. It uses the database only to look up internal ids for attack input, plant an expired session, and confirm nothing was changed or audited by a refused attempt. The committed report was generated against `npm run build` + `npm start`, because dev-mode pages are not byte-stable (see BUILD_LOG.md).
- Rejected and why: a hand-written table (nothing shows the attempts were actually made); running against `next dev` (responses differ run to run, and its 403 pages carry a stack trace).
- Files: scripts/check-access-control.ts, package.json (`check:access`), docs/evidence/access-control-audit.md

### What "no session" means for a page versus an API route
- Decision: how to read "replay with no session cookie, confirm it's a 401, not a redirect".
- Chosen: API routes return 401 `UNAUTHENTICATED`. Pages return a 307 redirect to /sign-in, as specified for the list and detail pages. Both carry no project data; the audit checks the redirect for alice's real id and for a nonexistent id are identical, for no cookie and for a forged cookie.
- Rejected and why: a 401 page for pages: the earlier brief asked for a redirect on pages.
- Files: docs/evidence/access-control-audit.md
